# Market-data fetch paths — Massive and Bloomberg: how they work, where the time goes, what to change

Measurements in this note were taken on 2026-09-23 at ~22:30 UTC (London ~23:30), i.e. after that day's US close: every "live" snapshot is the last NBBO of the 09-23 session. File references are `backend\volfit\...` unless stated. Vendor limits are labelled **[vendor doc]** when a page states them and **[unverified]** otherwise.

## Current implementation

### Massive REST — live chains (`data\massive.py`)

One pooled `httpx.Client` (keep-alive, Bearer header, 15 s timeout, HTTP/1.1; `_client` massive.py:255-265) serves every GET through `_get` (267-271) and `_paginate` (286-295, follows `next_url`). A chain fetch is:

1. **Contract listing** `available_expiries` (299-324): `/v3/reference/options/contracts?expired=false&limit=1000`, paginated; the ladder is cached per ticker in memory for the process (`_expiries_cache`). The same listing is pulled *again* by `_intraday_contracts` (920-954) under a different key `(ticker, frozenset(expiries))` for the WS subscription set, the as-of path and `option_tickers`.
2. **Snapshot** `_snapshot_results` (365-400): one query *per selected expiry*, `/v3/snapshot/options/{U}?expiration_date=…&limit=250` (`_SNAPSHOT_LIMIT` = 250, line 55 — the documented maximum, see Evidence), paginated serially inside each expiry; expiries run 2-wide (`_SNAPSHOT_WORKERS` = 2, lines 57-62: 3–4 workers measured slower, 8 hit read-timeouts). With no expiry selection the whole horizon is one *serial* paginated stream (`expiration_date.lte`, lines 395-400).
3. **Spot**: `underlying_asset.price` off the snapshot, else parity on the front expiry, else the stocks snapshot (fetch_chain 693-708). The scheduler's `autoUpdate="spot"` tick calls `spot()` (336-361) = one nearest-expiry snapshot (1–2 pages) per ticker.
4. **Streaming**: when a WS book is live, `fetch_chain(live)` reads `_chain_from_book` (641-644) and does **no REST** — the first fetch after the stream starts still goes to REST because the book has not implied a forward yet (645-646). The scheduler keeps the subscription in sync every second (`api\state_sources.py:95-134`), re-deriving the contract set from the (cached) listing.
5. **Status probe** `feed_status` (203-237): two single-page GETs. The selector polls `GET /datasources` every 30 s (`frontend\src\state\useDataSources.ts:52`) and the backend re-probes after `STATUS_TTL` = 30 s (`api\datasource.py:46`), so an open selector costs ~240 GETs/hour with nothing else happening.

Caching above the provider: none for Massive chains. `POST /fetch/snapshot` accepts `maxAgeSeconds` (`api\workflow_fetch.py:68-85`, `schemas.py:2380`) but only the MCP connector sends it (`volfit_mcp\ops.py:100`); the UI's Fetch never does (`frontend\src\state\useWorkflow.ts:317-321`). Chains refetch 8 tickers wide (`api\workflow.py:288-330`). The Bloomberg listing has a 600 s TTL (`bloomberg.py:113`), the exchange adapters a 60 s raw-chain TTL (`data\exchange.py:48-122`). Auto-update "snapshot" is floored at 15 s (`schemas.py:216, 861`).

### Massive history — as-of frames (`data\massive_history.py`, `massive.py:961-993`)

A past instant (EOD or intraday) is rebuilt **per contract**: `_intraday_contracts` (the 13-page listing unless cached), one synchronous probe quote (history.py:114-118), a spot hint (2 calls, 174-187), then up to `NBBO_MAX_CONTRACTS` = 1,500 calls to `/v3/quotes/{O:…}?timestamp.lte=…&limit=1`, `NBBO_CONCURRENCY` = 12 in flight (lines 40-43, 136-158), belly-first by |ln(K/S)|/√T (`budget_contracts` 56-77). There is no retry: a `NOT_AUTHORIZED` **or** a rate-limit `ERROR` body (`_quote_le` massive.py:969-972) raises, `_hist_nbbo_gate` is set for the *whole session* (history.py:117, 155) and every later past chain is served as marks. Nothing consults the store first: `AppState._fetch_asof` (`api\state.py:774-795`) goes straight to the provider for `eod`/`intraday`, and `_persist_capture` skips Massive (`NO_AUTO_CAPTURE_SOURCES`, state.py:809-813). The Series lens *does* store its frames as snapshots (`api\series_harvest.py:76` `save_snapshot(..., series_id=…)`), but the Smile lens never reads them back.

### Flat files (`data\flatfiles.py`, `backtest\quotes_store.py`)

The app's `FlatFileStore` reads `minute_aggs_v1` / `day_aggs_v1` through DuckDB+httpfs, filtering one whole day file to the watchlist roots into a local Parquet (`_ensure_cached` 183-201) — **marks only** (bid = ask = close, line 137). The two-sided `quotes_v1` product is the backtest's job: one non-splittable gzip per day, **111.41 GB** for one day (ROADMAP.md:8440), 4.8–8.85 h per scan (backtest\README.md:74, SPEC.md:163-164); the docs describe it only as "a daily downloadable S3 file" [vendor doc], no per-underlying slice. The backtest replaced it with the per-contract REST path at ~110 quotes/s, concurrency 40, async httpx with 429/5xx retry (`backtest\rest_quotes.py:4-15, 170-183`).

### Bloomberg (`data\bloomberg*.py`)

- **Session model**: xbbg 1.3.0 (pyo3) owns one lazily created engine/session for `bdp`/`bds`/`bdh` (`bloomberg_parse.py:62-92`); symbol search opens its own `//blp/instruments` session (`bloomberg_search.py:55-66`); the stream owns a third session on a daemon thread (`bloomberg_stream.py:282-325`, reconnect with capped backoff, subscribe in batches of 200).
- **Chain listing** `_chain` (bloomberg.py:396-456): three bulk requests — `OPT_CHAIN` (monthlies/LEAPS, both sides) + `CHAIN_TICKERS` with `CHAIN_PERIODICITY_OVRD` W and Q, `CHAIN_EXP_DT_OVRD=ALL`, `CHAIN_POINTS_OVRD=50000` (calls only, puts mirrored 142-154, yellow key appended 169-177); one root per date (`bloomberg_roots.py`, an `OPEN_INT` bdp only for contested dates without a parent root); cached **600 s** in memory (`CHAIN_CACHE_TTL` 113).
- **Quotes** `_fetch_live` (620-664): one `PX_LAST` bdp for spot, a strike window `[0.5, 1.5]×spot` (`strike_window` 223, 608-618), then **one** `bdp(securities, 6 fields)` over every selected contract (`_QUOTE_FIELDS` 94: BID, ASK, LAST_PRICE, VOLUME, OPEN_INT, OPT_EXER_TYP). xbbg sends it as one ReferenceDataRequest; blpapi splits it into groups of 10 securities × 128 fields internally [vendor doc]. Hits per fetch = securities × 6.
- **Streaming**: `//blp/mktdata` subscriptions (BID/ASK/LAST_PRICE/VOLUME, `interval=1`), windowed with 5 % hysteresis and capped at 3,000 securities nearest-the-money (`bloomberg_live.py:21-27, 42, 126-137`); while streaming, `fetch_chain` and `spot()` never bdp (bloomberg.py:537-538, 594-596).
- **History**: `bdh` over all contracts + underlying for one date, 5 fields (`bloomberg_history.py:42-56`); `available_history` = one PX_LAST bdh over 45 days.
- **Status**: quota-free (`feed_status` 326-359 reads session state + the last refusal recorded by `_record` 312-324). Refusal codes mapped in `bloomberg_parse.py:34-41` (WORKFLOW_REVIEW_NEEDED, DAILY/MONTHLY/RESPONSE_LIMIT_REACHED).

### Others (contrast)

Cboe: one CDN JSON per underlying (`data\cboe.py:9-25`: SPY 6 MB/~1 s, SPX 14 MB/~2 s), 60 s TTL, no key. Nasdaq: one JSON per class, SPY ~1.5 s (`nasdaq.py:22`). Yahoo: yfinance, one `option_chain(expiry)` call per expiry (`yahoo.py:15, 301`), ~2.7 s for a ladder (measured earlier today).

## Limitations

**Latency drivers.** Massive's cost is page count × ~0.1 s at 250 rows per page, with two things inflating it: per-expiry queries leave the last page of every expiry partly empty (342 rows → 2 pages, the second 37 % full) and the horizon-wide query is serial. The listing (1.4 s) is paid per ticker per process, twice (two caches), and again on any `refresh_contracts`. Bloomberg's cost is server-side: 5–16 s per bdp regardless of our code, ~70–200 securities/s, plus a 2–6 s `OPT_CHAIN` every 10 min; the wrapper blocks on one request at a time, so nothing overlaps.

**Throttle exposure.** Massive: the snapshot endpoint visibly resists concurrency (3–4 workers slower, 8 → timeouts — measured, not documented); no response carries rate-limit headers (probe: `x-item-count`, `x-request-id`, `link` only); the app neither counts calls nor retries, and a single rate-limit body on the history path degrades the whole session to marks. The status poll alone is 240 calls/hour. Bloomberg: the account is metered on **hits** (security × field; 500,000/day) and on **unique securities per month** (Bloomberg "recommends 4,000–5,000"; intraday data weighted higher) — both from a university library sheet, i.e. [unverified] as vendor-official; the 2026-06-15 `DAILY_CAPACITY_REACHED` and the 2026-09-10 `WORKFLOW_REVIEW_NEEDED` recurrence after 7.8k + 20k-contract pulls (memory `bloomberg-xbbg-workflow-gate.md`) are consistent with the *unique-securities* limit being the binding one: a single SPX chain quote spends ~20k unique securities, four times the recommended monthly budget, in one call. Requesting 6 fields multiplies daily hits by 6 while only BID/ASK feed the fit.

**Single points of serialisation.** Massive: `_paginate` inside one expiry; the horizon fetch; the listing; `spot()` per ticker per tick; the synchronous probe + spot hint before the 1,500-call fan-out. Bloomberg: one bdp per fetch, awaited whole; three sequential bds for the listing. App: `_fetch_asof` never consults the store, so every as-of view of the same instant re-spends 1,500 calls.

**1 — Retry and per-frame degradation.** `_quote_le` (massive.py:961-974) treats every `ERROR` body as fatal and `_fetch_nbbo_chain` (history.py:154-156) remembers it for the session. Port the backtest's `_get` (retry 3×, 0.5 s × attempt, on 429/5xx/timeout) into `MassiveProvider._get`, classify bodies — `NOT_AUTHORIZED` = entitlement (gate), "exceeded the maximum requests" = rate (back off, halve `NBBO_CONCURRENCY`, continue), 5xx = retry — and let a frame finish with the contracts it got. Honour `Retry-After` if it ever appears (none seen today).

**2 — Store-first as-of.** `_fetch_asof` (state.py:774-795) has the store handle and the source id; `snapshot_at` exists (store.py:432). One lookup before the provider call, one `save_snapshot(..., series_id=None)` after with a "reconstructed" tag the picker ignores, and the Series lens's frames (already rows) become the Smile lens's cache. This is the single largest interactive gain: a second look at any as-of instant becomes instant.

**3/4/5 — Fewer, fuller Massive pages.** The listing is the same 13 pages under two cache keys; one disk-cached listing per (ticker, day) removes 1.4 s from cold start, from the as-of path and from the WS resubscribe key. Per-expiry queries cannot fill pages; a strike window (docs support `strike_price.gte/lte`) shortens every expiry to one page for SPY-sized rungs, and the horizon fetch becomes two half-horizon shards, each a full-page stream — both inside the measured 2-wide concurrency limit. Byte-identity of fits holds only where the window contains everything the quote prep keeps (the deep-wing filter |k| ≤ 4·√w_atm, `backtest\SPEC.md:46`); pick the window from that rule, not from a fixed band.

**6/7 — Concurrency and a visible budget.** The history endpoint sustained 40 in flight for the backtest on this key; the app runs 12 and is ~100 ms/call bound. An adaptive window (AIMD on 429/timeouts) is a few lines in `_fetch_nbbo_chain`; a counter in `_get` surfaced through `feed_status`'s detail makes the spend visible and lets the status probe reuse the last real call instead of two fresh GETs every 30 s.

**8/9/10/11/12 — Bloomberg under its meters.** The Terminal is slow per security (5–16 s per bdp) and metered on hits and unique securities. Fields: BID/ASK are what the fit reads; the other four cost 4 of every 6 hits. Windows: the uniform [0.5, 1.5]×spot keeps 2,692 SPY securities across nine rungs whereas the front rungs need a ±5–10 % band — per-expiry windows cut the unique-securities spend, which is the limit that bit twice. Overlapping chunked requests are the only lever on wall time for the metered path and must be measured on a small chain first (the API groups 10 securities per internal request and allows 1,024 pending). The listing can be daily. Above all, the subscription book already gives quota-free quotes; making it the first-choice path when Bloomberg serves a pinned ticker removes the bdp entirely, and the listing (3 bds/day) becomes the only metered call.

**13/14 — Cross-source.** `maxAgeSeconds` is wired end-to-end but the UI never sends it; sending 15 s from the Fetch button makes the double-click and the Calibrate-after-Fetch free on every source. A fastest-green policy belongs in `source_of` (`state_sources.py:34-40`) as an explicit "auto" pin, never silent.
